Fixify AI diagnosis: how it works and how to demo it

A customer describes a home problem in words and photos. One Gemini call turns it into a structured diagnosis: trade, urgency, duration and parts. Everything here was checked in the code on branch dev (commit with the diagnosis cache) and run against a real server on 2026-11-12. JSON shown is copied from those runs.

!Fix before the demo

No code changes are needed. These are setup steps.

  1. Restart the server right before you present. The hourly limit counter and the diagnosis cache live in memory (middlewares/rate-limit.ts:27-38, libraries/ai/diagnosis-cache.ts:79). A fresh start gives Rana a full 10 analyses and an empty cache, so the first call is a real Gemini call and the second is a cache hit. Rehearsing on the same running server uses up that budget.
  2. Check .env: GEMINI_API_KEY and GEMINI_MODEL must both be set (they are), or analysis answers 503 AI_NOT_CONFIGURED (libraries/intake-analysis.ts:69-75). NODE_ENV=development must stay, or Swagger's "Try it out" is switched off (routes/docs.ts:18-21).
  3. Seed account: rana@demo.fixify / Demo1234! (scripts/seed-demo.sql:4,10). Both the fixify and fixify_verify databases were built with this seed.
  4. Pick the database. npm run dev uses DB_NAME from .env, so demo sessions are saved in your live fixify database. To keep it clean, start with $env:DB_NAME='fixify_verify'; npm run dev instead.
  5. Use a second account for the demo moments. Section 3 uses about 5 of Rana's 10 analyses per hour, and the four demo moments use 5 more. Log in as karim@demo.fixify / Demo1234! before section 4 (paste the new token in Authorize).
  6. Use the copy buttons for the problem text. The cache step only hits when the text is exactly the same. One changed character is a miss.
  7. The free tier can be busy. In one rehearsal the main model's answer was cut off and the fallback model answered 503 "high demand", so that session ended failed. If you see "aiStatus": "failed", run step 3 again. That uses attempt 2 of 3.
  8. Not tested: clicking through Swagger UI itself. Every request below was sent with curl to the same endpoints, and Swagger sends the same requests. Rehearse the clicks once.

1The flow at a glance

One message, from the app to the stored diagnosis. There are three HTTP calls: send the message, ask for the diagnosis, then poll for the result. The model call runs in the background so the app never waits on Gemini.

Your outline put the limiter after the cache. In the code it is the other way round: the hourly limiter runs at the route (routes/intake.ts:38-43) and the attempt cap in the service, both before the cache is checked. So a cache hit still counts toward both limits. That was a deliberate choice: it keeps the limits simple.

2The flow, step by step

  1. The message arrives

    When the user sends a message, it arrives in this form. It is a multipart form, not JSON, so photos can travel with the text. The route is mounted at app.ts:50 and defined at routes/intake.ts:23-28.

    POST /intake-sessions
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Content-Type: multipart/form-data

body   = "My kitchen sink has been leaking from the pipe underneath since this morning. There is a small puddle on the floor."
photos = (optional) up to 5 JPEG or PNG files, 5 MB each
    The customer's message comes in as a form, so photos can come with the text.

  2. Who is this? Authentication

    Every intake route runs authenticate first (routes/intake.ts:21). It verifies the JWT signature and expiry (libraries/jwt.ts:11-23) and attaches the user id (middlewares/authenticate.ts:5-19). No token or a bad token is 401.

    req.user = { "id": "00000000-0000-4000-8000-000000000001" }
    The login token is checked before anything else. Without it the request gets a 401.

  3. Input validation

    Photos are accepted only if their first bytes are really JPEG or PNG. The file name and the client's content type are ignored (middlewares/upload.ts:6-7, 21-53). Then zod checks the text: 1 to 2000 characters after trimming (routes/intake.schema.ts:4-6, middlewares/validate.ts:11-21). If neither text nor photo is sent, the request gets a 400.

    req.body          = { "body": "My kitchen sink has been leaking from the pipe underneath since this morning. There is a small puddle on the floor." }
res.locals.photos = []
    Input is validated at the edge, so the service only ever sees clean, typed data.

  4. Saved as an intake session

    The controller calls the service (controllers/intake.ts:15-26). The service writes the session, the message and the photo rows in one transaction (libraries/intake.ts:47-86).

    Response · 201
    {"session":{"id":"3866bdf5-9a02-492d-8b74-56fe980bf603","aiStatus":"none","createdAt":"2026-11-12T20:29:56.242"}}
    The message and its photos are saved together, in one transaction.

  5. The app asks for a diagnosis

    The request is POST /intake-sessions/{id}/analysis, with no body. The route runs authenticate, then the hourly limiter (10 per user, middlewares/rate-limit.ts:27-38), then checks that the id is a UUID (routes/intake.schema.ts:9-11), then the controller (controllers/intake.ts:77-84). The full chain is at routes/intake.ts:38-43.

    res.locals.params = { "id": "3866bdf5-9a02-492d-8b74-56fe980bf603" }
    Asking for a diagnosis is a separate call, and each user can make at most ten of them an hour.

  6. Service guards, then a 202

    startAnalysis (libraries/intake-analysis.ts:65-99) runs these checks:

    • Is the AI configured? If not, 503 (lines 69-75).
    • Is this the caller's session? If not, 404 (libraries/intake.ts:91-100).
    • Is there any text to diagnose? If not, 400 SESSION_HAS_NO_TEXT (lines 77-82).

    Then one guarded UPDATE (models-db/intake.ts:249-271) marks the session pending and counts the attempt. It succeeds only when the session has fewer than 3 attempts, is not already running and is not booked. When it is refused, startRefusal (lines 104-127) works out why. The analysis then starts in the background (line 89), and the call returns at once.

    Response · 202
    {"aiStatus":"pending"}
    The AI can take a few seconds, so we answer right away with 202 and do the work in the background. The app polls for the result.

  7. Load the conversation

    loadAnalysisInput (libraries/intake-analysis.ts:245-275) reads every message in order and the 6 newest photos as base64. Photos are only read from inside the intake upload folder (lines 277-283).

    {
  "messages": [
    { "id": 1, "sender": "customer", "body": "My kitchen sink has been leaking from the pipe underneath since this morning. There is a small puddle on the floor.", "createdAt": "2026-11-12T20:29:56.243", "photos": [] }
  ],
  "photos": []
}
    The model sees the whole conversation in order, plus at most the six newest photos.

  8. Cache check

    diagnoseOrReuse (libraries/intake-analysis.ts:193-240) builds a SHA-256 key from the prompt version, the configured model and the exact content sent to the model (libraries/ai/diagnosis-cache.ts:17-30). Session and message ids are not part of the key, so the same text from another session gets the same key. A hit skips Gemini completely. On a miss, if a call for the same key is already running, this request waits for that call instead of starting another (libraries/ai/diagnosis-cache.ts:83-101).

    key = sha256(JSON.stringify([4, "gemini-3.1-flash-lite", content]))   // 64 hex characters
hit  → { "model": "gemini-3.1-flash-lite", "diagnosis": { ... } }
miss → null
    If someone sent this exact problem in the last 24 hours, we reuse that answer and skip the model. No tokens, about 10 milliseconds.

  9. Prompt assembly

    The rules live in a fixed system instruction (libraries/ai/diagnosis-prompt.ts:39-100). It lists the 15 trades, the urgency and safety rules, and says the customer's text is information, not instructions (lines 44-45). buildContent (lines 124-159) labels each customer turn and puts each photo right after its message.

    [
  { "type": "text", "text": "Customer message 1:\nMy kitchen sink has been leaking from the pipe underneath since this morning. There is a small puddle on the floor." }
]
    The rules sit in a system instruction. The customer's words are labelled as customer messages and treated as data, never as commands.

  10. One model call, with a backup

    diagnose (libraries/ai/gemini.ts:70-106) makes one Interactions API call and forces a JSON reply that matches the schema. The SDK's own retries are turned off (line 105). Instead, hedgedDiagnose (libraries/ai/hedged-diagnose.ts:66-126) starts the fallback model if the main one hasn't answered after 12 s or fails, and the first valid answer wins. The whole analysis gets at most 45 s (lines 11-12).

    {
  "model": "gemini-3.1-flash-lite",
  "system_instruction": "You are the intake assistant for Fixify, a home-services app in Lebanon. ...",
  "input": [ { "type": "text", "text": "Customer message 1:\n..." } ],
  "response_format": { "type": "text", "mime_type": "application/json", "schema": DIAGNOSIS_JSON_SCHEMA },
  "generation_config": { "thinking_level": "low", "max_output_tokens": 1024 },
  "store": false
}
    There is exactly one AI call. It has to answer in our JSON schema, and if the main model is slow or fails, a backup model takes over.

  11. Parse and validate the answer

    The text is parsed with JSON.parse, then checked by zod field by field (libraries/ai/gemini.ts:111-163, libraries/ai/diagnosis-schema.ts:16-26). The category must be one of the 15 trades, the duration 15 to 1440 minutes, and there can be at most 10 parts. Empty output counts as blocked; bad JSON or a schema miss counts as invalid_output. A valid answer goes into the cache (libraries/intake-analysis.ts:226-231).

    {
  "title": "Kitchen sink pipe leak",
  "confidence": "high",
  "category": "Plumber",
  "serviceType": "repair",
  "durationMinutes": 60,
  "explanation": "You likely have a loose fitting or a cracked pipe under your kitchen sink. The plumber will inspect the drainage system and replace the damaged pipes or seals to stop the leak.     We never trust the model's reply. It's parsed and checked field by field, and anything out of range is rejected.

  12. Save to MySQL

    One transaction (libraries/intake-analysis.ts:142-156) sets ai_status = 'done' and stores the diagnosis JSON. The write only happens if the session is still pending (models-db/intake.ts:275-286), so a late answer after a timeout is thrown away. The explanation is also saved as the AI's chat message.   13. Log the outcome

    One info line per analysis (libraries/intake-analysis.ts:173-179). It never contains the prompt, the customer's text or the photos.

S6Hit the limits

6a · Double click (one diagnosis at a time). Go back to the first session's id in POST …/analysis and press Execute twice quickly. This re-run is a real Gemini call, because the AI's reply is now part of the conversation and that changes the cache key.

202 then 409 {"error":{"code":"ANALYSIS_PENDING","message":"A diagnosis is already running for this problem"}}

6b · Per-problem cap (3). Wait 2 to 3 seconds, then press Execute again on the same session (attempt 3, gets 202). Wait again and press once more:

429 {"error":{"code":"ANALYSIS_CAP_REACHED","message":"A problem can be diagnosed at most 3 times; choose a trade instead"}}

6c · Hourly limit (10 per user). Reaching it in Swagger takes about 6 more create-and-analyse rounds, which is too slow live. Show ratelimit-remaining going down instead, or run this in a second PowerShell window after pasting your token. It reuses the cached text, so it uses no tokens:

$t = "PASTE_TOKEN_HERE"
1..11 | ForEach-Object {
  $id = (curl.exe -s -X POST http://localhost:3000/intake-sessions -H "Authorization: Bearer $t" -F "body=My kitchen sink has been leaking from the pipe underneath since this morning. There is a small puddle on the floor." | ConvertFrom-Json).session.id
  "start $_ : " + (curl.exe -s -X POST "http://localhost:3000/intake-sessions/$id/analysis" -H "Authorization: Bearer $t")
  Start-Sleep -Milliseconds 300
}
429 {"error":{"code":"ANALYSIS_RATE_LIMITED","message":"Too many diagnoses this hour; try again later"}} with a Retry-After header.

Tested on 2026-11-12: starts 1–10 returned pending and start 11 returned the 429. Refused requests (409, 429, 400) are not counted (skipFailedRequests), but the header on a refused response still shows the count from before the refund.

{"email":"not-an-email","password":""}

5Evaluation: how we know the AI is good enough

Before the endpoint was built, the prompt and model were tested against a fixed set of 17 cases with known right answers (fixtures/diagnosis/cases.ts). They include safety cases, three languages, a car problem no home trade can fix, a photo that contradicts the text, a vague message and the injection attack. A replay script sends each case through the same prompt-building and Gemini call as production, then checks the answer automatically.

The checks
scripts/replay-diagnosis.ts:252-299 (excerpt)
if (expect.category) {
  checks.push({ name: "category", pass: expect.category.includes(d.category) });
}
if (expect.isUrgent !== undefined) {
  checks.push({ name: "isUrgent", pass: d.isUrgent === expect.isUrgent });
}
if (expect.safetyNote !== undefined) {

6Mechanisms around the model call

Caching IMPLEMENTED

  • The key is a SHA-256 of the prompt version, the configured model and the exact content sent to the model. The same input from any session gets a hit.
  • Only valid diagnoses are stored. A hit is saved to the session exactly like a fresh answer.
  • Hits still count toward the 3-per-problem cap and the 10/hour limit.
  • Identical requests that arrive while the first call is still running share it. In a real test, 5 parallel requests made 1 Gemini call.
  • Hits and misses are counted, and the running hit rate is logged on every analysis (cacheStats).
  • Separately, reopening a session shows the stored diagnosis without a new call (libraries/intake.ts:155-170).
TTL 24 h diagnosis-cache.ts:10 max entries 500, oldest evicted diagnosis-cache.ts:11, 37-77 store in-process memory diagnosis-cache.ts:79 lookup intake-analysis.ts:193-240

Next step: a cache that survives restarts and works across several server processes. Today it lives in one process's memory.

Rate limiting and usage caps IMPLEMENTED

  • 10 analysis starts per user per hour. The limiter is keyed by user id, and refused requests are not counted. Responses carry RateLimit-* headers.
  • 3 analyses per problem, enforced by one guarded SQL UPDATE, so two parallel requests can't both get through.
  • One analysis at a time per session (409 ANALYSIS_PENDING).
  • A 429 from Gemini itself sends the job to the fallback model.
hourly 10 / 60 min rate-limit.ts:27-38 per job 3 intake-analysis.ts:51 guard models-db/intake.ts:249-271 login 20 / 15 min rate-limit.ts:14-23

The counters are in memory, so a restart resets them. That's fine with one server process.

Token and cost control PARTIAL

  • A hard cap on output tokens, which includes the model's thinking. Thinking level is set to low.
  • At most 6 photos and 2000 characters per message go to the model.
  • Cache hits use zero tokens.
  • Every call's token use is logged. A real call: 1010 input, 234 output, 132 thinking.
  • Runs on Gemini's free tier.
max_output_tokens 1024 gemini.ts:33 thinking_level low gemini.ts:32 photos per call 6 intake-analysis.ts:52 usage logged gemini.ts:112-116

Next step: a running token total per user or per day, with a budget alert. Today usage is only logged per call.

Context management IMPLEMENTED

  • The whole conversation goes in, in message order. Each customer turn is labelled, and each photo comes right after its message.
  • Earlier AI replies are included and labelled, so "here is the photo you asked for" makes sense.
  • Limits: the 6 newest photos per call, 20 photos per session, 2000 characters per message.
buildContent diagnosis-prompt.ts:124-159 loadAnalysisInput intake-analysis.ts:245-275 20 photos/session libraries/intake.ts:37

With these limits the input stays small, so long conversations don't need summarising.

Timeouts, retries, fallbacks IMPLEMENTED

  • A hedged call: the fallback model starts after 12 s, or at once if the main model fails. A 400 never triggers the fallback, because it means our request is wrong. The first valid answer wins and the other call is cancelled.
  • The whole analysis gets 45 s. A late answer is thrown away by the guarded UPDATE.
  • The SDK's automatic retries are turned off. The fallback takes their place.
  • At startup, sessions stuck in pending are marked failed.
  • With no AI configured, the endpoint answers 503 and the customer picks a trade by hand.

Input sanitization and prompt injection PARTIAL

  • Customer text is labelled "Customer message N", kept separate from the rules.
  • The output is boxed in: a JSON schema, fixed lists for category and confidence, and zod re-checks every field.

src/libraries/ai/diagnosis-cache.ts:83-101
export function createInFlight<T>() {
  const running = new Map<string, Promise<T>>();
  return {
    run(
      key: string,
      start: () => Promise<T>
    ): { promise: Promise<T>; shared: boolean } {
      const existing = running.get(key);
      if (existing) return { promise: existing, shared: true };
      const promise = start().finally(() => running.delete(key));
      running.set(key, promise);
      return { promise, shared: false };
    },
  };
}

export const inFlightDiagnoses = createInFlight<HedgedDiagnosis>();
